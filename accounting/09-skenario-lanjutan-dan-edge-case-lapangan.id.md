# 09. Skenario Lanjutan & Edge Case Lapangan

> Prasyarat: seluruh master data (§00) + minimal 1 siklus transaksi (§01) sudah ada, dan file ini idealnya dikerjakan **setelah** §02-§08 supaya baseline data (Trial Balance, saldo per akun) sudah dikenal. File ini SENGAJA lebih "berat" — tiap skenario menembus lebih dari 1 fitur sekaligus, dan mensimulasikan kesalahan/urutan operasi yang realistis terjadi di lapangan, bukan cuma jalur normal happy-path.
>
> **Cara baca kolom "Label temuan"** (dipakai tiap kali hasil aktual tidak sesuai ekspektasi ideal, atau ekspektasi memang belum ada guard-nya):
>
> - 🆕 **Fitur baru** — belum ada mekanismenya sama sekali di kode, butuh desain+implementasi baru kalau mau ditutup.
> - 🔧 **Improvement kecil** — fiturnya sudah ada dan jalan untuk kasus umum, tapi kasus mirip-tapi-beda ini belum di-handle (biasanya guard tambahan atau validasi tambahan di titik yang sudah ada).
> - ✅ **Sudah tercover** — dites di sini untuk regresi, bukan karena diduga gap.
>
> Endpoint utama: **Accounting Period**, **Journals**, **Fiscal Year**, **Assets**, **Budgets**. Halaman UI yang dipakai: `/client-master/accounting-period`, `/client-master/fiscal-year`, `/accounting/journals` (+ `/accounting/journals/{slug}` untuk detail), `/fixed-assets/assets/{slug}`, `/accounting/budgets`, `/reports/trial-balance`.

## Konsep Dasar Tambahan (Khusus File Ini)

File ini beda nuansa dari 00-08 — istilah yang belum dikenal di sini kebanyakan istilah PENGUJIAN PERANGKAT LUNAK, bukan akuntansi murni:

| Istilah                          | Keterangan                                                                                                                                                                                                                                                        |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Immutable (tidak bisa diubah)** | Prinsip bahwa data yang sudah "final" (mis. period yang sudah closed) seharusnya TIDAK bisa diam-diam berubah lagi lewat jalur manapun — kalau ternyata masih bisa diubah (§9.5), itu pelanggaran prinsip ini dan dianggap serius karena merusak kepercayaan pada laporan yang sudah dianggap final.                                                                                             |
| **Race condition / tidak deterministic** | Kondisi di mana hasil akhir sistem tergantung URUTAN kebetulan (mis. mana yang diproses lebih dulu), bukan aturan yang jelas — bahaya-nya: hasil bisa beda-beda di percobaan berbeda meski input sama persis, susah direproduksi ulang saat debugging (§9.3, §9.6). |
| **Edge case**                    | Kondisi "di pinggiran" yang jarang terjadi tapi tetap mungkin (mis. angka pembulatan, tanggal masa depan) — beda dari jalur normal (happy path) yang dites di file 00-08. Diuji terpisah di sini justru karena gampang terlewat kalau cuma tes jalur normal.        |
| **Asymptotic (mendekati tapi tidak pernah pas nol)** | Istilah matematika: sebuah nilai terus mengecil mendekati angka tertentu tapi secara rumus murni tidak pernah PERSIS sampai di angka itu (§9.9) — di dunia nyata duit tidak bisa pecahan tak terhingga, jadi butuh aturan pembulatan khusus di ujungnya.        |
| **Post-dated (bertanggal masa depan)** | Transaksi yang dicatat sekarang tapi tanggalnya di masa depan (§9.7) — bukan kesalahan otomatis, tapi tetap perlu dicek apakah sistem sengaja mengizinkan atau seharusnya memperingatkan.                                                                        |
| **Label temuan (🆕/🔧/✅)**        | Sudah dijelaskan di catatan pembuka file ini — cara membedakan "belum ada fiturnya sama sekali" vs "fiturnya ada tapi ada kasus pinggiran yang belum di-handle" vs "sudah benar, ini cuma regression check".                                                        |

## 9.1 Guard Close Period — Period Berikutnya Wajib Ada & Terbuka (fitur baru 2026-08-04)

Guard baru: `AccountingPeriod::close()` sekarang menolak close kalau period berikutnya (by `start_date`, branch sama) belum ada, atau sudah closed/locked juga — mencegah gap seperti yang kejadian di data lama (lihat §9.2).

Semua aksi close/reopen di bawah dilakukan dari halaman **Client Master → Accounting Period** (`/client-master/accounting-period`): buka menu titik-tiga (⋮) di baris period yang mau diproses → pilih **Close Period**/**Reopen Period**. Kalau tombolnya disabled, hover untuk lihat alasan spesifik langsung di label menu (mis. "(period is already closed)").

## 9.3 Periode Tumpang Tindih — Data Integrity Edge Case

`resolveCurrent()`/`resolveCurrentForDisplay()` sama-sama pakai `->first()` tanpa `orderBy` eksplisit kalau ada lebih dari 1 period yang date range-nya overlap untuk tanggal yang sama (harusnya tidak mungkin lewat form normal, tapi tidak ada constraint DB yang mencegahnya).

| Skenario                                                       | Detail                                                                                                                                                          | Hasil                                                                                                                                                                                                                           | Label temuan                                                                                                                                                                                                                                                       |
| -------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Negatif — buat 2 period overlap secara sengaja**             | Di halaman **Client Master → Accounting Period**, klik **+ Add** dua kali untuk `FY-TEST`, buat 2 period dengan Start Date/End Date yang overlap (mis. Period X: 1-31 Jan, Period Y: 15 Jan - 14 Feb) → **Create** untuk masing-masing | Toast sukses untuk keduanya, kedua baris muncul di list — **tidak ada validasi yang menolak overlap saat create/update**                                                                                                                                             | 🆕 **Fitur baru** — `create()`/`update()` accounting-period seharusnya menolak kalau date range-nya bertabrakan dengan period lain di branch+fiscal year yang sama                                                                                                  |
| **Negatif — cek mana yang dipilih `resolveCurrentForDisplay`** | Set tanggal hari ini jatuh di overlap kedua period itu, lalu reload halaman Accounting Period atau lihat sidebar widget indikator period aktif                                                                         | Salah satu period muncul dengan badge "Current" (yang mana tergantung urutan row di DB, biasanya `id` terkecil karena tidak ada `orderBy`) — **tidak deterministic secara sengaja**, cuma kebetulan konsisten selama tidak ada perubahan urutan insert | 🔧 **Improvement kecil** — sambil menunggu fix §create (item di atas), `resolveCurrent()`/`resolveCurrentForDisplay()` sebaiknya tetap ditambah `orderBy('id')`/`orderBy('start_date')` eksplisit supaya perilakunya predictable, bukan bergantung urutan fisik row |
| Netralisasi                                                    | Buka ⋮ di masing-masing baris period overlap test → **Delete** sebelum lanjut                                                                                                              |

## 9.9 Penyusutan Saldo Menurun — Book Value Tidak Boleh Di Bawah Nilai Residu

Lanjutan §6.2 — declining balance dihitung dari book value berjalan, secara matematis nilainya makin kecil tapi TIDAK PERNAH benar-benar mencapai nol persis (asymptotic). Kalau dijalankan sampai `useful_life_months` habis, ada risiko pembulatan bikin book value turun di BAWAH `residual_value`.

| Skenario                                                             | Detail                                                                                                                                                                                                                                                 | Hasil                                                                                                                                                                                                                                                                           | Label temuan                                                                                                                                                                                                    |
| -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

## Ringkasan Prioritas Kalau Mau Ditindaklanjuti Jadi Perbaikan Kode

Urutan berdasarkan potensi dampak riil ke integritas data (bukan urutan file):

1. **§9.5** (reverse period closed) — kalau lolos, ini pelanggaran prinsip "closed period = immutable", paling berbahaya buat kredibilitas laporan keuangan yang sudah difinalisasi.
2. **§9.3** (period overlap) — sumber bug tersembunyi paling licin karena gejalanya baru muncul kalau data sudah kadung tumpang tindih (sulit didiagnosis setelahnya).
3. **§9.4** (pesan error gap vs closed) — murni UX, tidak berisiko data, tapi bikin user salah tindakan (reopen padahal harusnya generate).
4. Sisanya (§9.6, §9.7, §9.8, §9.9, §9.10) — nice-to-have / kandidat fitur baru, tidak mendesak.

> **§9.1 poin "close Desember sebelum FY berikutnya ada"** sudah diperbaiki di sesi yang sama (bukan lagi item terbuka) — dicatat di sini supaya riwayatnya kebaca, lihat tabel §9.1.
