# 03. Tutup Periode & Tahun Fiskal

> Prasyarat: master data (§00) + minimal 1 siklus transaksi (§01) sudah ada. Endpoint: **Accounting Period**, **Fiscal Year — `close-year`**.

## Konsep Dasar Tambahan (Khusus File Ini)

| Istilah                          | Keterangan                                                                                                                                                                                                                                                                                                                                                                             |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Close vs Lock (2 gerbang, bukan 1)** | **Close** (§3.1) = "tutup buku" bulan itu — mencegah jurnal BARU masuk, tapi masih bisa dibuka lagi (`reopen`) kalau ternyata ada koreksi. **Lock** (§3.2) = gerbang lebih kuat, cuma bisa dipasang SETELAH periode closed — begini urutannya sengaja bertingkat supaya ada jeda waktu untuk double-check sebelum benar-benar "dikunci mati". Reopen tetap bisa membuka keduanya sekaligus kalau memang perlu (lihat §3.2 Netralisasi).                                          |
| **Closing entry (jurnal penutup)** | Jurnal otomatis KHUSUS yang dibuat sistem saat `close-year` — tugasnya cuma satu: menge-nol-kan SEMUA akun Pendapatan & Beban (supaya tahun berikutnya mulai dari nol, bukan kebawa saldo tahun lalu), dan memindahkan selisihnya (laba/rugi bersih) ke akun **Laba Ditahan** (Retained Earnings) yang sifatnya permanen (akun Neraca, TIDAK di-nol-kan tiap tahun).                 |
| **Kenapa harus tepat 1 akun Laba Ditahan** | Sistem butuh SATU tujuan pasti untuk "parkir" laba/rugi tahun itu. Kalau 0 akun ber-flag ini, sistem tidak tahu mau taruh ke mana → ditolak daripada nebak. Kalau lebih dari 1, sistem juga tidak tahu yang mana yang benar → ditolak juga, supaya tidak diam-diam pilih salah satu (lihat pola yang sama untuk `is_opening_balance_equity_account` di §00 §3).                    |

## 3.1 Tutup Periode Bulanan (Accounting Period Close)

Skenario: akhir Januari 2026, akuntan PT Retail Nusantara Jaya menutup periode Januari supaya tidak ada lagi jurnal yang bisa masuk ke bulan itu.

| Skenario                              | Langkah di UI                                                                                                                                  | Hasil                                                                                                                      |
| ------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| Positif                               | Pastikan semua jurnal Januari (§01) sudah **posted** (bukan draft) → buka halaman **Accounting Period** → menu **⋮** baris periode Januari → **Close Period** → konfirmasi | Toast sukses, kolom **Closed** di baris tabel berubah jadi badge merah "Closed", tercatat di `ActivityLogger`                                                                        |
| **Negatif — ada jurnal belum posted** | Buat 1 jurnal manual draft baru bertanggal Januari (belum di-post) via Create Journal → buka **Accounting Period** → menu **⋮** baris Januari → **Close Period**                                   | Toast error: `accounting_period_has_unposted_journals_post_or_void_them_first` — akuntan harus post atau hapus dulu jurnal itu |
| Negatif                               | Buka periode yang sudah Closed → menu **⋮** — opsi **Close Period** sudah disabled di UI dengan keterangan "period is already closed"; untuk verifikasi backend, test tetap via API call: `PUT client-master/accounting-period/close`                                                                                                       | Ditolak `accounting_period_already_closed`                                                                                 |
| Netralisasi                           | Menu **⋮** baris periode → **Reopen Period** → konfirmasi                               | `is_closed:false`, jurnal baru bisa posting lagi ke periode ini                                                                                                            |

**Sebab-akibat:** guard "ada jurnal belum posted" ini penting karena draft itu belum resmi (lihat status jurnal di file 01) — kalau periode dibiarkan closed padahal masih ada draft nyangkut, draft itu jadi "terjebak" (tidak bisa di-post lagi karena periodenya sudah tutup, tidak bisa dihapus kalau sudah ada nilainya) sampai periode dibuka lagi. Guard ini memaksa akuntan menyelesaikan semua urusan bulan itu dulu sebelum benar-benar ditutup.

## 3.2 Kunci Periode (Lock) — Gerbang Lebih Kuat dari Close

| Skenario                                       | Langkah di UI                                                                                      | Hasil                                                                                    |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| Positif                                        | Periode Januari sudah berbadge Closed → buka **Accounting Period** → menu **⋮** baris Januari → **Lock Period** → konfirmasi    | Toast sukses, kolom **Locked** di baris tabel berubah jadi badge warning "Locked"                                                                    |
| Negatif                                        | Pilih periode yang belum Closed → menu **⋮** — opsi **Lock Period** sudah disabled di UI dengan keterangan "period must be closed before it can be locked"; untuk verifikasi backend, test tetap via API call: `PUT client-master/accounting-period/lock`                                                       | Ditolak: `accounting_period_must_be_closed_before_it_can_be_locked`                      |
| **Negatif — posting ke periode closed/locked** | Buka jurnal draft bertanggal Januari (setelah periode di-lock) → klik **Post** di halaman detail jurnal | Toast error `no_active_accounting_period` (guard `JournalPostingService::createGlEntries()`) |
| Netralisasi                                    | Menu **⋮** baris periode → **Reopen Period** → konfirmasi                        | `is_closed:false, is_locked:false` sekaligus                                                                                                          |

**Sebab-akibat:** baris "posting ke periode closed/locked" adalah bukti bahwa Close/Lock bukan cuma status kosmetik di layar — begitu periode ditutup, backend BENAR-BENAR menolak transaksi baru masuk ke tanggal itu (bukan cuma tombol yang disembunyikan di FE). Ini penting karena laporan yang sudah dianggap "final" untuk bulan itu (dan mungkin sudah dikirim ke pihak luar) tidak boleh berubah diam-diam kalau ada yang lupa dan tetap mencoba posting.

## 3.3 Tutup Tahun Fiskal (Fiscal Year Close) — Closing Entry Sungguhan

Skenario: akhir Desember 2026, semua 12 periode sudah closed, akuntan menutup tahun buku 2026 — sistem otomatis membuat jurnal penutup yang menge-nol-kan semua akun Pendapatan & Beban ke akun Laba Ditahan.

**Prasyarat WAJIB sebelum test ini** (kedua guard ini akan menolak kalau belum terpenuhi):

1. **Semua 12 Accounting Period FY2026 harus `is_closed:true`** — untuk test murni fiscal-year-close, cukup close periode Januari-Desember satu-satu dulu (ulangi §3.1 untuk tiap bulan; kalau tidak ada transaksi di bulan itu, tetap bisa di-close karena tidak ada jurnal draft untuk diblokir).
2. **Tepat 1 akun ber-flag `is_retained_earnings_account:true`** — yaitu akun 3102 Laba Ditahan dari §00. Kalau 0 atau lebih dari 1, akan ditolak.

**Sebab-akibat:** angka `net_income` di baris "Positif" bukan angka yang bisa ditebak-tebak — itu HARUS persis sama dengan hasil hitung manual (Total Pendapatan − Total Beban dari semua transaksi §01), karena itulah cara memverifikasi closing entry menghitung dengan benar. Kalau angkanya beda dari hitungan manual, berarti ada transaksi yang salah kebaca (mis. kelewat atau kehitung dobel) — laporkan sebagai temuan, jangan anggap "mungkin memang segitu".

## 3.4 Kaitan dengan Balance Sheet — Kenapa Closing Entry Penting

Sebelum fiscal year ditutup, Neraca (`reports/balance-sheet`) menampilkan baris sintetis "Current Year Earnings" di section Equity (dihitung on-the-fly dari Pendapatan−Beban tahun berjalan). Setelah `close-year` dijalankan, laba tahun itu sudah benar-benar masuk sebagai saldo permanen di akun Laba Ditahan — baris "Current Year Earnings" untuk periode SETELAHNYA akan otomatis mulai dari nol lagi (bukan reset manual, tapi karena akun Pendapatan/Beban memang sudah di-nol-kan). Lihat detail pengujian di [`04-laporan-keuangan.id.md`](./04-laporan-keuangan.id.md) §4.1.

## 3.5 Dashboard Accounting — "Periode Ini" Harus Ikut Accounting Period Aktif (Regression Check)

**Halaman:** `/dashboard/accounting` — widget KPI **Net Income This Period** dan **Income Statement** (di kartu ringkasan dashboard), plus konteks **Period** yang ditampilkan (Fiscal Year + Accounting Period aktif).

**Sebab-akibat:** sebelum 2026-08-10, widget ini hardcode rentang "bulan kalender berjalan" (`now()->startOfMonth()` s.d. hari ini) — TIDAK mengikuti Accounting Period yang sedang ditampilkan di label sebelahnya. Kalau kamu baru mulai pakai sistem dan langsung nyicil input transaksi backdated (skenario umum banget di awal onboarding — persis seperti §00 §9 dan semua transaksi §01 yang ber-tanggal Januari 2026 padahal diinput hari ini di bulan lain), widget ini akan diam-diam menampilkan `0/0/0` padahal label **Period** di sebelahnya menunjukkan bulan yang penuh transaksi. Ini membingungkan karena tidak ada tanda error — angkanya cuma salah lihat rentang tanggal. Sudah difix supaya `income_statement`/`net_income_this_period`/`top_accounts` di dashboard mengikuti `start_date`/`end_date` dari Accounting Period yang sedang aktif ditampilkan (`periodStatus.period`, hormat ke mode manual/auto pemilihan periode aktif — lihat commit "manual and auto modes for accounting period management"), bukan kalender riil.

| Skenario                                                              | Langkah di UI                                                                                                                                                                                                                     | Hasil                                                                                                                                                                                                                                                                            |
| ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Positif — regression check bug "0/0/0" saat transaksi backdated** | Pastikan Accounting Period yang aktif ditampilkan di dashboard (label **Period**) adalah periode yang benar-benar berisi transaksi (mis. Januari 2026 dari §01), meski tanggal hari ini di sistem sudah jauh lebih baru (Agustus 2026 dst) → buka **Dashboard → Accounting** | Kartu **Net Income This Period** dan **Income Statement** menampilkan angka SESUAI transaksi di periode yang ditampilkan (bukan `0/0/0`) — sama persis dengan hasil `reports/income-statement` untuk rentang tanggal periode itu. Kalau dashboard nunjukin `0/0/0` padahal label Period menunjukkan bulan yang ada transaksinya, ini regresi ke bug lama — laporkan segera |
| Positif — verifikasi silang ke report asli | Bandingkan angka `net_income` di kartu dashboard dengan `net_income` hasil Run Report di halaman **Reports → Income Statement** untuk rentang tanggal Accounting Period yang sama | Harus identik persis, karena dashboard memanggil `ReportController::incomeStatement()` yang sama secara in-process, cuma beda rentang tanggal input |
